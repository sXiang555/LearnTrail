# 用事务守住一次积分解锁

积分解锁看起来只是“减去一些积分，再允许观看”。真正需要设计的，是重复点击、网络超时与中途失败时，余额、流水和学习权益还能否相互对应。

本文结合 LearnTrail 的实际链路，讨论一个可落地的本地事务设计。重点是说明每一道检查解决什么问题，以及它的边界在哪里。

## 一、先明确三个需要一起变化的结果

一次成功解锁会同时改变三类数据：钱包余额减少、业务流水增加、读者获得学习权益。它们表达的是同一笔业务，不能让其中任意一项独立成功。

| 数据 | 作用 | 需要维持的关系 |
| --- | --- | --- |
| 积分钱包 | 保存当前可消费余额 | 余额不能因同一次解锁重复减少 |
| 业务流水 | 记录这次解锁的原因与金额 | 同一用户、同一业务目标只记一次 |
| 学习权益 | 决定读者能否访问完整内容 | 扣分成功后必须能查到对应权益 |

![钱包、流水与学习权益在同一个事务内提交或回滚](/images/points-transaction.svg)

这三个结果都位于学习服务使用的数据库中，因此可以放进同一个数据库事务。课程信息和播放授权仍由各自的服务提供，不应把所有服务都塞进这笔本地事务。

## 二、调用链从服务端身份开始

浏览器提交的是课程标识。用户身份来自已经验证的登录上下文，解锁价格也由服务端查询，不接受浏览器自行指定的用户或扣分金额。

本文用于讲解本地事务的兼容入口是：`POST /ls/studio-points/unlocks/{courseId} → StudioPointsController.unlock → StudioPointsService.unlock`。

2026-11-11 的页面入口已改为 `Checkout.vue → POST /ts/point-orders → 订单详情页支付 → PointsOrderService.pay → PointsSettlementService.pay`，支持单张积分券，并在学习服务本地事务中提交钱包、流水、结算凭证与权益。下文的直接解锁片段仍是现有兼容实现，不代表当前页面绕过订单，也不覆盖跨服务订单和券的完整结算流程。

学习服务随后通过 `CourseClient.studioUnlockCost` 调用课程服务，最终由 `StudioService.unlockCost` 和 `StudioMapper.findUnlockPoints` 检查专栏状态、运营屏蔽标记及解锁积分。

把条件检查放在后端的意义在于：页面按钮可以改善体验，但浏览器之外的请求也必须遵守同一套规则。余额不足、内容下架、身份无效等情况，都需要在真正写入之前被拒绝。

## 三、钱包行锁让同一账号的扣分串行执行

假设同一个读者在两个标签页同时点击解锁。两个请求如果先分别读取相同余额，再各自扣减，就可能把“看起来足够”的余额重复使用。

当前链路锁定的是该读者的钱包行。相同账号的后续扣分请求需要等待，拿到锁后再继续检查业务流水和权益。

```sql
SELECT balance
FROM learntrail_point_wallet
WHERE user_id = :userId
FOR UPDATE;
```

这里的 `:userId` 表示绑定参数。它来自服务端身份，而不是直接拼接浏览器提交的字符串。

锁的粒度也很重要：按用户钱包加锁，可以串行化同一账号的消费，同时让不同账号继续独立操作。它并不是把整个积分平台锁住。

## 四、事务中的核心顺序

查询解锁条件后，服务锁定钱包并判断是否已有有效权益。如果已有权益，直接复用；如果没有，再检查是否已经为这门课程扣过积分。

下面是现有 `StudioPointsService.unlock` 中与写入有关的关键片段，省略了课程校验与响应对象的组装：

```java
if (mapper.hasEntry(user, "UNLOCK", courseId) == 0) {
    if (balance < cost) {
        throw new BadRequestException("积分不足，请先阅读文章获取积分");
    }
    changeBalance(user, -cost);
    mapper.addEntry(user, "UNLOCK", courseId, course.getName(), -cost);
    balance -= cost;
}

mapper.grantLesson(IdWorker.getId(), user, courseId);
lessonId = mapper.validLesson(user, courseId);
if (lessonId == null) {
    throw new IllegalStateException("学习权益创建失败");
}
```

方法由 `@Transactional` 管理。扣分、写流水、授予权益必须一起提交；权益没有成功创建时抛出异常，前面的数据库写入随事务回滚。

还需要配合有条件的余额更新，避免余额被写成负数：

```sql
UPDATE learntrail_point_wallet
SET balance = balance + :amount
WHERE user_id = :userId
  AND balance + :amount >= 0;
```

服务检查受影响行数。更新失败时不能继续假定扣分成功，也不能向读者返回已经取得权益的结果。

## 五、重复请求要识别同一笔业务

行锁解决了并发执行顺序，但用户稍后再次请求，仍然需要业务层识别“这次解锁已经完成”。因此还要查询学习权益与解锁流水。

`learntrail_point_entry` 使用 `(user_id, kind, target_id)` 作为复合主键。对于解锁，业务类型是 `UNLOCK`，目标就是课程 ID。

| 请求时的状态 | 当前处理方式 |
| --- | --- |
| 已有有效权益 | 返回已有权益，不再扣分 |
| 没有权益，也没有解锁流水 | 检查余额，扣分、记账并创建权益 |
| 已有解锁流水，权益需要重新加入课表 | 恢复权益，不重复扣分 |
| 余额不足 | 拒绝操作，不创建新的解锁结果 |

这里使用的是明确的业务键。它可以保护当前的积分解锁场景，但不能直接被称为覆盖所有消息和交易的“完整幂等系统”。不同业务仍需要各自的身份和状态约束。

## 六、拥有权益与获得播放授权是两件事

学习权益记录读者是否有资格观看，播放器仍需要针对具体小节取得播放授权。完整目录不能只依赖前端把锁图标隐藏。

播放请求经过 `MediaServiceImpl.getPlaySignatureBySectionId`，调用课程服务获取小节信息，并结合试看配置、创作者身份和有效学习权益判断访问范围。

这种划分让专栏下架与运营屏蔽可以表达不同的含义：

- 创作者下架后，停止新的公开发现和解锁，已有权益仍可观看最后已发布的内容。
- 运营屏蔽后，停止新的播放授权和讨论。
- 已经签发的播放链接有自己的有效期，当前最长为两小时，并不支持即时回收。

最后一项是当前实现的真实边界。改变数据库状态，并不会自动让已经发到浏览器中的地址立刻失效。

## 七、阅读奖励使用同样的记账思路

站内非外链文章首次有效阅读默认奖励 20 分，要求累计有效阅读 30 秒且读至正文 80%，每日默认上限 200 分；服务端读取 `learntrail_point_rule` 校验，不是打开页面就发奖。重复阅读通过 `READ + 文章 ID` 的唯一业务记录识别，不重复增加余额。

钱包与原签到积分、积分排行榜保持独立。这样，可消费余额和学习行为的累计得分不会混用同一套账目。

外部资料的导读只提供原作者、介绍和原文入口，无法代表读者已经读完外站全文，因此不发放站内全文阅读奖励。

## 八、检查关键边界

评估这条链路时，可以把请求结果和数据库里的余额、流水、权益对应起来，而不是只看页面是否出现“解锁成功”。

1. 首次解锁后，扣分金额应与服务端价格一致，并能查到真实权益。
2. 重复请求后，余额不应再次减少，解锁流水仍只有一条。
3. 余额不足时，不应出现新的扣分流水或权益。
4. 同账号并发请求后，不应产生多次扣分。
5. 已有权益的内容下架后，访问历史内容的规则仍应保持一致。
6. 修改未更换视频的分集后，原小节 ID 和观看进度应尽量保留。

这些检查把“事务、并发和幂等”落到了可以观察的业务结果上。至于跨服务事件、消息确认和播放链接即时撤销，还需要额外设计和验证，本地事务不会自动解决它们。
